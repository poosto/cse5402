❯ how to fix the else case

● Two things going on in the else branch:

  1. Double brackets. {:?} on a Vec<String> (or a slice) already renders with
  brackets and quotes, e.g. ["foo", "baz"]. Your format string wraps it in
  literal [...] too, so you'd get [["foo", "baz"]]. Drop the manual [ and ] from
  the string and let {:?} do it.

  2. Wrong type being formatted. arg_vec.into_iter().skip(1) gives you an
  iterator (a Skip<...> struct), not a collection. Printing that with {:?} won't
  give you the clean ["foo", "baz"] look — it'll show the iterator's internal
  debug representation, not a nice list. Also, .into_iter() consumes/moves
  arg_vec, so you can't easily also reference arg_vec[0] in that same println
  for the program name.

  Instead, look at slicing: &arg_vec[1..] gives you a slice of everything after
  index 0, without moving or consuming the vector, and slices implement Debug
  the way you want (prints as ["foo", "baz"]).

  Also double check: your task description says the else branch should include
  the program name in the message (like the usage line does) — right now your
  else branch drops it entirely. You'll want two {}/{:?} placeholders in that
  println!, similar to how the if-branch uses arg_vec[0].

❯ why do i need &                                                               

● arg_vec[1..] on its own is a slice ([String]) — a dynamically-sized type. Rust
  needs to know the size of things at compile time to put them on the stack,
  and a slice's length isn't known until runtime, so you can't have a bare
  [String] as a value — it has to be accessed through a pointer of some kind.

  &arg_vec[1..] takes a reference to that slice — &[String] — which is just a
  pointer + length, a fixed-size "fat pointer" the compiler is happy with. This
  also means you're borrowing from arg_vec rather than moving/consuming it,
  which is exactly why this approach doesn't fight you with ownership issues the
  way .into_iter() did (that one takes ownership and drains arg_vec, so you'd
  lose access to arg_vec[0] afterward).

  So & here is doing two things at once: (1) satisfying the sized-type
  requirement for indexing/slicing, and (2) letting you borrow instead of move,
  so arg_vec is still usable elsewhere in the same statement.
