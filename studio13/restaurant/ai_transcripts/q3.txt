  How each pattern maps to the code

  - Active Object (src/kitchen.rs): waiters never touch the chef directly. They
    call KitchenProxy::place_order, which turns the call into a MethodRequest
    and puts it on a channel. A kitchen thread takes requests off that channel
    one at a time and hands each to the Chef, which does the cooking.
  - Half-Sync/Half-Async: the async half is the waiters. place_order returns
    right away, so a waiter keeps taking orders while the chef cooks. The
    channel sits between the two halves. The sync half is the chef, who blocks
    on each order until it's cooked.
  - Leader/Followers (src/pass.rs): the "pass" is the counter where finished
    plates go. One waiter at a time is the leader and watches it. When a plate
    shows up, the leader picks it up, hands leadership to a waiting follower,
    and then carries the plate out. When the kitchen closes, the shutdown passes
    from waiter to waiter until all of them have exited.
  - Orders (src/order.rs): OrderStatus is Ordered, Ready or Served. Each change
    prints a line like [READY  ] order #4 table 17 ....
  - Setup (src/main.rs): there are 4 waiter threads. Each gets 5 tables of its
    own (1–5, 6–10 and so on), and each table gets 2–6 customers at random
    (src/rng.rs). There is one order per table.

  One thing to decide: I read "bringing food back to their tables" in the
  classic Leader/Followers way. Whichever waiter is leader carries the plate,
  even to another waiter's table. The output shows both waiters, for example
  table 16 (Waiter 4's table) brought out by Waiter 3. If you meant that each
  waiter should only serve their own tables, the leader would have to pass
  plates to the right waiter. That change is small, but it moves away from
  classic Leader/Followers.

❯ does state.has_leader not need to be atomic?                                  

⏺ No, it doesn't need to be atomic. has_leader lives inside Mutex<PassState>, so
  every read and write of it happens while the lock is held:

  let mut state = self.state.lock().unwrap();   // lock held from here
  while state.has_leader {
      state = self.leader_free.wait(state).unwrap();
  }
  state.has_leader = true;

  - The lock covers it. Only one thread can hold the lock at a time, so two
    waiters can never read or write has_leader at the same moment. The lock also
    makes sure each thread sees the latest value, which is the job an atomic
    would otherwise do.
  - Rust enforces this. The only way to reach state.has_leader is through the
    guard that lock() returns. If you tried to touch it without the lock, the
    code would not compile.
  - wait is safe too. Condvar::wait gives up the lock while it sleeps and takes
    it back before it returns. So the while state.has_leader check always runs
    with the lock held.

  An AtomicBool by itself would actually be worse here. "Check that there's no
  leader, then become leader" has to happen as one step, together with the sleep
  and wake logic and with the plates queue. With a separate atomic, a thread
  could check the flag and decide to sleep, and the wakeup could fire before it
  actually starts waiting. That wakeup would be lost and the waiter would sleep
  forever. Keeping all the shared state under one mutex and using condvars
  avoids that whole class of bug.
