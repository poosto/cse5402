7) *As the answer to this exercise please explain briefly why the main thread cannot end until the other thread exits its loop.*
The `join()` call of the other thread blocks until it is able to be joined. Since it is in an infinite loop, it will never join until the program is explicitly killed. Therefore, the main thread cannot end either.

8) *Compile and run your program and confirm that the program terminates normally. As the answer to this exercise please
explain briefly why it was necessary to make an extra call to connect after setting the flag.*
```rust
use std::env;
use std::io::{self, Read, Write};
use std::net::{Shutdown, TcpListener, TcpStream};
use std::sync::atomic::{AtomicBool, Ordering};
use std::thread;

static FLAG: AtomicBool = AtomicBool::new(false);

fn main() -> io::Result<()> {
    let listener = TcpListener::bind("127.0.0.1:7878")?;
    let handle = thread::spawn(move || -> io::Result<()> {
        loop {
            let (mut stream, _addr) = listener.accept()?;

            let mut text = String::new();
            stream.read_to_string(&mut text)?;

            if !text.is_empty() {
                println!("recv: {text}");
            }

            if FLAG.load(Ordering::Relaxed) {
                break Ok(());
            }
        }
    });

    let mut stream = TcpStream::connect("127.0.0.1:7878")?;

    stream.write_all(
        &env::args()
            .skip(1)
            .fold(String::new(), |mut accum, arg| {
                if !accum.is_empty() {
                    accum.push(' ');
                }

                accum.push_str(&arg);

                accum
            })
            .into_bytes(),
    )?;

    stream.shutdown(Shutdown::Write)?;
    FLAG.store(true, Ordering::Relaxed);
    TcpStream::connect("127.0.0.1:7878")?;

    handle.join().expect("Server thread panicked")?;

    Ok(())
}
```
The extra `connect` call is necessary because there is a race condition. If the other thread reads `FLAG` before the
main thread writes to it, it will read `false` and wait for another connection. However, the main thread will then write
`true`, and the other thread will spin forever in a deadlock. The extra `connect` guarantees the loop runs again. A
better design would be some sort of waker signal that provides a notification for when the server should terminate. The
server would listen to both the waker and to the TCP connection, and if the waker ever pushes a message, terminate. The
static flag is passive, versus a waker which is active.

there is only one `Rc` in our program and moving it is safe. However, if the `Rc` were to be cloned and that clone was
moved into the other thread, this could cause a data race when incrementing the reference count across both threads
(when dropped). Thus, the program errors:

An `Arc` can always be safely moved across threads, because the reference count is incremented atomically. Again, even though this program is safe with an `Rc`, there is no way for the compiler to know that. You must either use an `Arc` or `unsafe` code.
