❯ why does rust do it that way?                                                 

⏺ Because main returning Result is meant for any error type, not just numbers.
  The standard library has one generic impl, roughly:

  impl<T: Termination, E: Debug> Termination for Result<T, E> {
      fn report(self) -> ExitCode {
          match self {
              Ok(val) => val.report(),
              Err(err) => {
                  eprintln!("Error: {err:?}");
                  ExitCode::FAILURE
              }
          }
      }
  }

  The only thing it asks of the error type E is Debug, so it can print the
  error. Here's why it doesn't use your u8 as the exit code:

  1. Most error types have no obvious code. E is usually something like String,
     std::io::Error or your own struct. There's no general way to turn those
     into an exit code, so Rust picks the one safe answer: "failed"
     (ExitCode::FAILURE, which is 1 on Unix).
  2. Stable Rust can't special-case u8. A separate impl for Result<(), u8> would
     overlap with the generic one. Choosing the more specific impl needs a
     feature called "specialization", which is still unstable, so the standard
     library can't ship it.
  3. Exit codes differ across operating systems. Unix keeps only 8 bits (0–255),
     while Windows uses 32-bit codes. ExitCode::FAILURE means "failure" on
     every platform. Turning arbitrary error values into raw codes wouldn't be
     portable.

  So Result<(), E> from main is a convenience: Error: ... on stderr and a
  nonzero exit. If you want specific exit codes, Rust expects you to return
  ExitCode yourself or implement Termination on your own type. That second
  option is exactly what ReturnWrapper does. Your Error: 3 currently looks right
  only because Debug for u8 prints just 3.

  is:

  enum AppError { BadArgs, Script(String) }

  impl AppError {
      fn exit_code(&self) -> u8 { match self { AppError::BadArgs => 1,
  AppError::Script(_) => 2 } }
  }

  impl std::fmt::Display for AppError { /* human-readable message */ }

  fn run() -> Result<(), AppError> { /* all the logic, using ? freely */ }

  fn main() -> ExitCode {
      match run() {
          Ok(()) => ExitCode::SUCCESS,
          Err(e) => { eprintln!("error: {e}"); ExitCode::from(e.exit_code()) }
      }
  }

  66 for missing input, and so on). For this lab, stick with the u8 wrapper the
  spec asks for. You could mention the enum alternative in your Return Wrapper
  subsection as a design choice you considered.

❯ why empty impl Eq                                                             

⏺ Eq has no methods. It's a "marker trait": implementing it is a promise about
  how your PartialEq behaves, not new code.

  - PartialEq provides ==. It doesn't require that every value equals itself.
  - Eq adds that requirement (reflexivity: a == a is always true). That's what
    makes == a full equivalence relation, alongside symmetry and transitivity,
    which PartialEq already expects.

  The standard example of a type without it is f64. NaN == NaN is false, so
  floats implement only PartialEq, and you can't call .sort() on a Vec<f64> or
  use a float as a HashMap key.

  Why you need it: Ord requires Eq (trait Ord: Eq + PartialOrd), and Vec::sort
  requires Ord. So without impl Eq for Player {}, your Ord impl won't compile.

  Why it's yours to get right: the compiler can't check the promise; it trusts
  you. Your comparison is by first line number, which is a usize, plus the
  silent/silent case, so every player equals itself and the promise holds. If
  you ever compared floats inside eq, the promise could be false and sorting
  might behave strangely.

  #[derive(Eq)] would produce the same empty impl. The spec asks you to
  implement the traits yourself, though, so writing it out matches it best.

❯ why do it as a markertrait?                                                   

⏺ Because there's nothing new to compute. PartialEq::eq already does the
  comparison. Eq only adds the claim that eq also satisfies a == a for every
  value. Here's why Rust expresses that as a trait with no methods:

  1. Generic code can require the property. A marker trait is something you can
     put in a bound. HashMap<K, V> needs K: Eq + Hash, and sort needs T: Ord,
     which implies Eq. Both rely on reflexivity: a hash map has to find a key
     equal to itself, and sorting needs a consistent total order. So
     HashMap<f64, _> or vec_of_floats.sort() fails at compile time instead of
     misbehaving at runtime, like losing entries keyed by NaN.
  2. The compiler can't check the property. In general, whether an arbitrary eq
     function is reflexive is undecidable. Rust can't verify it, so it has you
     state it explicitly. Then a broken promise is a bug you can point to in one
     place.
  3. A method would have nothing to do. An is_reflexive() method could only
     check reflexivity by testing every possible value, and its answer is fixed
     per type anyway. A type-level fact with no runtime cost is exactly what a
     marker trait is for.
  4. The alternatives are worse. Without the split, there would be one equality
     trait, and floats would either break it or get special-casing. Java's ==
     says NaN != NaN, but Double.equals says NaN equals itself, so collections
     and plain comparisons disagree. Rust's split makes the difference visible
     in the type system.

  Rust uses the same pattern elsewhere. Copy promises that a bitwise copy is a
  valid duplicate, and Send/Sync promise thread safety. The compiler derives
  Send and Sync automatically when it can prove them. Implementing them by hand
  requires unsafe, because breaking those promises can cause memory errors, not
  just odd results.

  tell you which one comes first. That's a new question with a new answer
  (Less/Equal/Greater), so it needs a method, partial_cmp.

  return type:

  - partial_cmp returns Option<Ordering>.
  - cmp returns Ordering.

  promise says it's never None. With cmp, the type itself says "always
  comparable", so callers never unwrap.

  So Ord is partly a promise, like Eq, and partly a method with a more precise
  signature. That's also why the Clippy lint exists: cmp and partial_cmp both

✻ Cooked for 16s · done 8:56 PM

❯ couldnt PartialEq return some other type then                                 

⏺ It could have; that was a design choice. There are two reasons Rust kept it as
  bool.

  1. "Partial" means something different for the two traits.
  - In PartialEq, "partial" means a partial equivalence relation: symmetric and
    transitive, but not necessarily reflexive. It doesn't mean "sometimes can't
    answer." For any two values, "equal" or "not equal" is always a valid
    answer. NaN == NaN is just false, so a bool covers every case.
  - In PartialOrd, "partial" means a partial order, where some pairs really are
    incomparable. NaN vs 1.0 is not Less, not Equal and not Greater. None of the
    three Ordering values would be truthful, so partial_cmp needs None to say
    "incomparable." There's no equivalent gap for equality, so PartialEq doesn't
    need an Option.

  2. Practicality and hardware. IEEE 754, the floating-point standard, defines
  comparisons involving NaN as false, and CPUs implement them that way. bool
  matches what the hardware does. == also appears in nearly every if, so an
  Option<bool> would force an unwrap or a match on every comparison of every
  type, just to handle floats.

  A related point: Rust fixes == to return bool. PartialEq::eq must return bool,
  so you can't overload == to return something else, the way C++ allows. Array
  libraries like ndarray and polars would like an element-wise a == b that
  returns an array of booleans. They can't, so they offer methods like .eq()
  instead. Rust gives up some flexibility so that == always means a plain yes or
  no.
✻ Sautéed for 11s · done 8:57 PM

❯ so partial equivalence means u can still compare the two, it's just false?    

⏺ Yes. With a partial equivalence relation you can always compare any two values
  and get a definite true or false; nothing is incomparable. It's "partial"
  because some values aren't equal to themselves.

  The rules are:
  - Symmetric: if a == b, then b == a.
  - Transitive: if a == b and b == c, then a == c.
  - Not required: reflexive (a == a). Adding that requirement turns it into a
    full equivalence relation, which is what Eq promises.

  Those two rules lead to a useful fact. A value that isn't equal to itself 
  can't be equal to anything. If a == b held, symmetry would give b == a, and
  transitivity would then give a == a. That's exactly what NaN does: NaN == NaN,
  NaN == 1.0 and NaN == NaN_from_somewhere_else are all false.

  So you can picture a partial equivalence relation as an ordinary equivalence
  relation on the "well-behaved" values. For floats, that's everything except
  NaN. The remaining values sit outside it and equal nothing, not even
  themselves. Asking about them is still allowed; the answer is just always
  false.

  Ordering is different. There, NaN vs 1.0 has no truthful answer among
  Less/Equal/Greater, which is why partial_cmp can return None.

✻ Baked for 7s · done 8:58 PM

❯ why arent they defined in the same way, like why isnt partialeq option bool   

⏺ They actually are defined the same way at the operator level. The Option shows
  up only because of what partial_cmp returns.

  The operators all return bool. ==, <, >, <= and >= each ask a yes/no question.
  With NaN, every one of them returns false:

  NaN == 1.0  // false
  NaN <  1.0  // false
  NaN >  1.0  // false

  Each of these operator methods (eq, lt, gt, ...) returns bool, so PartialEq
  and PartialOrd treat the two kinds of question the same way.

  The difference is partial_cmp. It answers a different kind of question: not
  "is a < b?" but "which of the three relationships holds?" Its answer type is
  Ordering, which has exactly three values: Less, Equal and Greater.
  - For NaN vs 1.0, all three are false.
  - If partial_cmp had to pick one, it would be wrong. For example, returning
    Greater would imply NaN > 1.0, which contradicts the > operator.
  - So it needs a fourth answer, "none of these", and that's None.

  Equality doesn't have this problem. A yes/no question always has a truthful
  answer: "is NaN equal to 1.0?" is "no". bool already includes the "not equal"
  answer as false, so nothing extra is needed. An Option<bool> would add a third
  state, "can't say," that never applies, and it would cost an unwrap on every
  ==.

  In short, the Option exists only because a three-way answer can't express
  "incomparable", while a yes/no answer always can.

❯ but is NaN equal to NaN is undeterminable no?                                 

⏺ Philosophically, you have a point. NaN means "the result of an undefined
  operation," like 0.0/0.0 or sqrt(-1.0). Asking whether two undefined results
  are equal arguably has no answer. SQL takes that view: NULL = NULL evaluates
  to UNKNOWN, using three-valued logic.

  IEEE 754, which Rust follows, makes a precise choice that resolves this. It
  says any two floats are in exactly one of four relations: less, equal,
  greater, or unordered. Any comparison involving NaN is unordered. Each
  operator then asks one specific question about that relation:

  - a == b: "is the relation equal?" For NaN the relation is unordered, so the
    answer is no, and false is correct.
  - a < b: "is the relation less?" Again no, so false.
  - a != b: "is the relation anything but equal?" Yes, so true.

  So "how do NaN and NaN relate?" does have an answer: unordered. Rust's
  partial_cmp returns those same four states: Some(Less), Some(Equal),
  Some(Greater) and None (unordered). partial_cmp(NaN, NaN) is None, and == is
  false because unordered isn't equal. The two traits agree with each other.

  Here's the "undeterminable" part, put precisely:
  - == returning false means "not known to be equal," not "proven different."
  - This is also why Eq exists. Code that needs "false means different", like
    HashMap, can require Eq and reject floats at compile time.

  Rust could have chosen SQL's three-valued approach, but SQL shows the cost.
  WHERE x = NULL never matches anything, so you need a separate IS NULL
  operator, and it's a well-known source of bugs. Rust kept == as a plain bool
  that matches the hardware, and made the "unknown" case explicit only where
  it's needed: partial_cmp's None, and the PartialEq vs Eq split.
