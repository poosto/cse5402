⏺ No. Player::prepare handles one part file for one character. The spec
  signature is:

  pub fn prepare(&mut self, part_file_name: &String) -> Result<(), u8>

  The loop over play_config belongs in Play::process_config. The spec says that
  method should, for each (name, file) tuple, call Player::new(name), push the
  new player into the play's vector, and call player.prepare(file). So the for
  loop and valid_character_count move out of Player. What's left in prepare is:

  1. Read the part file into lines. If that fails, return Err.
  2. Call self.add_script_line(&line) for each line.
  3. Call self.lines.sort() and return Ok(()).

  part_file_name is already a parameter, so use it where you have
  character_file_name now.

  One spec change to decide on: the spec says that if prepare fails,
  process_config "should return an appropriate error". That replaces Lab 1's
  behaviour of skipping an unreadable part file and carrying on. Whichever way
  you go, explain it in the Structs section of the ReadMe.

  Some other things in player.rs that won't compile yet:
  - grab_trimmed_file_lines call: prepare calls it without the &mut lines
    argument.
  - add_script_line receiver: it takes &self but pushes into self.lines, so it
    needs &mut self. The spec says "a reference to itself", and it has to be
    mutable here.
  - add_script_line first warning: it still uses character_name. Change that to
    self.name, like the second warning already does.
  - grab_trimmed_file_lines placement: it doesn't use self, and
    Play::read_config will need it too. It reads the config and script files,
    and Lab 1's read_config already used it. The spec says code used by more
    than one module goes in declarations.rs. So I'd make it a plain pub fn

  - new parameter type (minor): the spec says new takes a reference to a String,
    and yours takes &str. Callers can still pass a &String, and &str is the
    more idiomatic choice. If you keep it, mention it in the ReadMe so the
    grader sees it was deliberate.

❯ should ad script line take mut self                                           

⏺ Yes, but it should be &mut self, not mut self:

  fn add_script_line(&mut self, line: &String)

  - &mut self borrows the player mutably, so self.lines.push(...) changes the
    player that prepare is working on. That's what you want.
  - mut self would take the player by value. The method would push into its own
    copy, which gets thrown away when the method returns. It also moves the
    player, so you couldn't call it again inside prepare's loop.

  This compiles because prepare already takes &mut self, so it can call
  self.add_script_line(&line).

  The spec's &String is shown above. Your current &str also works and is the
  more idiomatic choice, as with new.

❯ min works with Iterator<option<T>>?                                           

⏺ In my snippet, min never sees Options. filter_map removes them first:

  .enumerate()                                  // Iterator<Item = (usize, 
  &Player)>
  .filter_map(|(idx, player)|                   // closure returns 
  Option<(usize, usize)>
      player.next_line().map(|line| (line, idx)))
                                                // -> Iterator<Item = (usize, 
  usize)>, None entries dropped
  .min()                                        // -> Option<(usize, usize)>

  - filter_map keeps the value inside each Some and drops every None. Players
    with no lines left simply disappear from the iterator.
  - min() runs on plain (line, idx) tuples. It returns Option only because the
    iterator might be empty, and an empty iterator means every player has
    finished: that's your break.

  About min on Options directly: that also compiles, because Option<T> can be
  ordered whenever T can. But None counts as smaller than any Some. Once one
  player ran out of lines, min would return Some(None) and that player would win
  every time. Using filter_map before min avoids that.
