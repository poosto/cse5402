❯ why does clippy want new and default if they do the same thing                

⏺ Clippy doesn't want two constructors for their own sake. It wants your type to
  work with generic code, and only Default can do that. Rust has no trait for
  new.

  new is just a naming convention. Play::new() is an ordinary associated
  function. People look for it, and the spec asks for it, but code that doesn't
  know the concrete type can't call it.

  Default is a trait, so generic code can use it. A lot of the standard library
  and other crates build values through T: Default:

  - #[derive(Default)] on any struct that has a Play field. It only compiles if
    Play: Default.
  - option.unwrap_or_default()
  - std::mem::take(&mut play), which swaps in Play::default()
  - map.entry(key).or_default()
  - struct update syntax: Foo { x: 1, ..Default::default() }

  If a type has new() but no Default, all of those fail, even though the type
  clearly has an obvious "empty" value. The lint new_without_default exists to
  catch that gap. It only fires when new is public and takes no arguments,
  because that's exactly when new and default mean the same thing.

  Why keep both instead of just Default? Play::new() reads more clearly at the
  call site and is what people expect to find. Also, new can be a const fn on
  stable Rust, but Default::default can't. So the usual idiom is to keep both
  and have one call the other, so they can never drift apart:

  pub fn new() -> Self {
      Self::default()
  }

  Your derive does the same job. The only risk is that if someone later changes
  the body of new, default won't follow. Having new call Self::default() removes
  that risk.

  there, push, and run git pull on your Mac.

  Why oscyank didn't work

  oscyank sends the text to your terminal with an "OSC 52" escape code. Your
  Mac's terminal then has to put it on the clipboard, and many terminals ignore
  that code:

  - macOS Terminal.app: as far as I know, it doesn't support OSC 52, so the copy
    silently goes nowhere.
  - iTerm2: supports it, but you have to turn it on under Settings > General >
    Selection > "Applications in terminal may access clipboard".
  - tmux on the server: it also needs set -g set-clipboard on, or it swallows
    the code.

  For short output like the run_tests.sh results, the easiest way is to select
  the text with the mouse and press Cmd+C. You could also run sh run_tests.sh > 
  run_tests_out.txt on the server and scp that file back the same way.
