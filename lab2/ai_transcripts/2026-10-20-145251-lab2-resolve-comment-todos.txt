⏺ Your fix builds cleanly, but I'd change it. Removing Play::new doesn't follow 
  the spec. The step that adds the Fragments field says:

  ▎ "modify the associated new function so that it initializes the struct with 
  ▎ an empty Fragments field."

  So the grader expects a Play::new() to exist. Also, what Clippy's original
  new_without_default warning asks for is a Default impl alongside new, not one
  that replaces it.

  Your manual impl Default also causes a new Clippy warning. derivable_impls
  says the impl just builds an empty Vec, so #[derive(Default)] does the same
  thing in one line.

  Suggested fix: put back new, call it from main.rs again, and derive Default:
  #[derive(Default)]
  pub struct Play {
      fragments: Fragments,

❯ how do i write sort by key?                                                   

⏺ Replace self.lines.sort(); at player.rs:40 with:

  self.lines.sort_by_key(|&(line_number, _)| line_number);

  How it works:
  - The closure picks the sort key. Each element is a (usize, String), and the
    closure gets a reference to one. The pattern &(line_number, _) takes out the
    line number and ignores the text. The _ doesn't move the String, so this
    compiles without errors.
  - Only the line number is compared, so lines with the same number count as
    equal.
  - sort_by_key is a stable sort, which means equal elements keep their original
    order. So duplicate line numbers stay in file order.

  A shorter version does the same thing, but the pattern makes clearer what the
  key is:
  self.lines.sort_by_key(|line| line.0);

  It's been in std since long before Rust 1.71, so that's fine. After the
  change, delete the TODO and add a short comment saying why, for example:
  // Sort by line number only. The sort is stable, so lines with the same
  // number keep the order they had in the part file.

❯ is sort() also stable assuming two identical tuples                           

⏺ Yes. Vec::sort() is a stable sort too. Stability only matters for elements
  that compare as equal. Two identical tuples compare as equal, so sort() keeps
  them in their original order.

  But for identical tuples it doesn't make a difference. If both line number and
  text are the same, the two elements look exactly alike, so you can't tell
  which one came first in the output.

  The two sorts differ in what counts as "equal":
  - sort() compares the whole tuple. It looks at the line number first, then the
    text. So (12, "Zounds") and (12, "Ay") are not equal, and sort() reorders
    them by text.
  - sort_by_key compares only the line number. So those same two tuples are
    equal, and stability keeps them in file order.

  Both sorts are stable. They just disagree on which elements are ties. The only
  case where sort() changes the file's order is same number with different
  text. That's exactly the case where sort_by_key keeps file order.
